# 账号采购与使用成本

在配置文件设置 `"costTrackingEnabled": true` 后启动服务，登录管理后台打开「账号成本」。凭据卡片的「查看账号成本」可直达该账号。管理端使用原有 Admin API 密钥。

- 按凭据录入每笔采购的 CNY 实付金额、实际可用积分、付款、生效和到期时间。续费和加购新增批次。已预付的历史剩余额度用「期初余额」录入剩余积分及其成本，报表期间现金支付不重复统计。
- 使用成本按每次出站调用的积分报告分摊。套餐优先，加购最后，同类优先消耗较早到期的批次。每笔批次金额分摊保留 8 位小数，尾差在用完时合拢。
- 到期的本地批次停止分摊。确认上游权益到期后，可将该批次未用部分确认为损失。支出、使用、剩余及损失各有独立口径。
- 已付款但尚未生效的批次计入「待生效成本余额」，到期但未确认的残额计入「待确认到期损失」。这两项同时出现在汇总和账号表。付款、使用及确认损失是期间发生额；余额是截至期末的存量，不能直接把几张卡片当作同一个加法等式。
- 选择今天、本月或近几天查看整体成本，点击凭据 ID 查看采购批次及近 100 条出站尝试。报表可导出 JSON。日期筛选采用浏览器本地时区，接口接受 RFC3339 的 `from`、`to`（左闭右开）。

采集从启用时开始，原始计量数字存入与凭据文件同目录的 `costs.db`。报表按调用时间计算，如果补录的批次生效于过去，重新查询该期间会按新增批次分摊先前用量。保留凭据数据目录和一致的 SQLite 备份，运行中请使用 SQLite backup API。多套独立凭据应使用不同数据目录。使用管理端新增和删除凭据，更换实际账号需新增凭据。删除凭据后历史可按原 ID 查询。

余额快照使用已有刷新结果，供人工对账参考。缺失或部分计量、没有采购单覆盖的积分、独立 MCP 计量不可用均单列。账本写入异常时采集质量可能下降。历史覆盖、上游实际扣账和外部客户端用量需结合余额或账单判断。当前记录已知预付成本与到期损失，超额费用、退款及共享池需要单独对账。

管理操作及报表接口位于 `/api/admin/costs`。报表的货币和积分数值以十进制字符串返回。采购写入用请求体 `id`（UUID）实现幂等，相同请求重试应使用相同 ID。

## 采集、查询与退出

- 导入凭证不强制录入成本。期初余额应填写该余额实际对应的时点；将今天的剩余额度倒填到更早日期，会再次扣掉中间用量。
- 调用开始只入队，不等待 SQLite 落盘；每次计量和结束记录携带调用主体及已收计量，可补建失败的 Start，结束记录也会重放之前写入失败的计量。按调用 ID 和序号幂等写入，保留 `WAL + synchronous=FULL`。结束阶段仍有入队、确认各 250ms 的等待上限。
- 写事务最多尝试三次，每次 SQLite 锁等待上限 2 秒。采集异常会将相关记录标记为部分计量；累计异常数在后续成功写入或正常退出时保存，重启后继续显示。异常次数不是丢失调用次数，也不受当前账号和日期筛选限制。
- 恢复副本每个调用最多保留 256 条计量，超出时明确标记部分计量。队列容量仍为 2048 条命令。持续磁盘故障、所有恢复写入均失败、队列持续饱和或强杀进程时，仍可能丢失尚未持久化的事实；不能据页面金额推断完整真实成本。
- 原始计量保留原文。可参与分摊的单条及单调用累计积分须非负、不超过十亿，最多 18 位小数；采购积分须大于零且满足相同范围。超出范围、无法解析及负值被隔离为部分计量，不将未知值当零。有效的 16 位小数样本不会被舍入。汇总若超出精确计算能力，返回 `totalsAvailable=false` 和空金额，而非报表 500 或近似值。
- 查询使用可重建的 UTC 每日分摊检查点，每个查询范围（全池或单账号）保留最近 400 个。首次查询或历史补录后可能重放较多记录；日常查询从开始日期之前最近的检查点继续。采购变更、迟到计量及历史调用变更会使受影响日期之后的检查点失效。保存时检查并发历史变更，避免发布过时结果。
- 检查点只保存派生分摊状态，原始账本不按日志保留期删除。数据库仍会随原始调用增长，应纳入数据目录的容量规划和备份。导出的 JSON 是当前报表快照：单账号最多包含 100 条近期调用，全池不包含完整调用明细。
- 页面成本查询超时为 60 秒，有计算中和超时提示。页面明确区分「部分覆盖」与「尚未对账」；两者都不代表已经和上游账单核对一致。
- 正常 SIGTERM / Ctrl+C 会先停止接单，最多等待在途请求 30 秒，再最多等待成本队列排空及写线程结束 15 秒。未结束的调用标记为中断；排空失败会记录错误。仓库 Compose 配置预留 60 秒退出宽限；独立 docker run / 编排部署也应预留超过 45 秒。SIGKILL 不会执行退出流程。

## 成本库损坏时

成本库无法读取不再阻断网关启动，已有编号的凭证可继续提供服务。由于损坏的库可能保留着已删除账号的历史编号，此时暂时拒绝导入新凭证和自动分配编号；无编号的现有记录保留在凭证文件内，暂不参与调度。恢复原 `costs.db` 及一致的 WAL/备份后重启，编号分配即可恢复。不要为绕过此保护直接删除成本库，否则可能破坏历史归属。
